# P4 延迟剖析

> 数据：单轮来自 `p3-final-full-dev`（450 条）；SQLite 读写和真实 LLM 调用耗时来自 `p4-mt-full-dev`（60 段对话，改写调用均未命中本地缓存）。
> 测量时 PC 上同时运行着用户的其他程序，并且有 4 个工作线程，以下是端到端的墙钟时间。

## 结论

- 单轮的瓶颈在**规划**（beam search 加上每个完整候选的官方常识自检，占 46.6%）和**检索**（占 42.0%）。检索节点 P50 约 1.8 s，远高于 P2 单线程检索评测中每个子查询约 21 ms 的水平（每条查询约 5–10 个子查询）。差距应主要来自 4 线程并发与 torch 线程之间的 CPU 争用，本轮**未做单独剖析**，不作进一步归因。
- 多轮场景下，一次真实 LLM 改写调用的 P50 约 1,235 ms；SQLite 的 load_memory 和 save_memory 的 P50 分别约 58 ms 和 193 ms，大约是一次 LLM 调用的 1/20 和 1/6。**存储不是主瓶颈，但在这台机器上不可忽略**。原因：工作区位于 NTFS（fuseblk）卷，单次 SQLite 提交实测约 34 ms（读约 1 ms），save_memory 每轮会提交 3 次以上，4 个线程还会竞争锁。如果需要优化，可以把每轮写入合并为一个事务；本轮不做（不在范围内）。
- 对 v0 的判断不变：真正的耗时在 LLM 调用和规划/检索计算上，用 Redis 做短期记忆带不来可感知的提速；v1 使用 SQLite 单一事实源，代价是每轮约 0.25 s 的本地写入。
